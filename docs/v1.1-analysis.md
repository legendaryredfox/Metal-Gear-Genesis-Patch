# Analysis of the Metal Gear v1.1 ROM (Mega Drive)

English · [Português](v1.1-analise.md)

Record of the study behind the v1.1 patches, and of the things that were checked and **not** applied. Tags: **[OBSERVED]** seen in the code or in a run, **[INFERRED]** a conclusion drawn from what was seen, **[UNVERIFIED]** a proposal or hypothesis nobody ran.

## 1. Target and method

- ROM: `Metal Gear (v1.1).md`, 1,572,864 bytes, SHA-256 `8073e3f1e966d8f6ab5b97f4d7e96208dd32dbea01997c3a4b5e2c5195b06f8b`. Released 2025-05-14, updated 2025-05-18 (fixes leaving Outer Heaven by the ladder and the duplicated sprite save when using the binoculars).
- Tools: REA with Ghidra 12.1.3 (open as `raw-binary`, architecture `m68k`, entry `0x0`; 646 procedures), `m68k-linux-gnu-objdump -D -b binary -m m68k:68000`, this repository's Musashi simulator and BlastEm under xvfb.
- The header declares ROM end `0x13FE5C`; the file is zero-padded up to `0x180000`. The free area used by the patches is `0x13FE80-0x13FFFF`.

## 2. v1.1 compared with v1.2

**[OBSERVED]** The game code is the same as v1.2, shifted. The sound library is an older SGDK version (v1.2 uses the XGM2 driver).

| What | v1.1 | v1.2 |
|------|------|------|
| Boot RAM clear (`movew #n,d7`) | `0x4A0` | `0x49C` |
| Call that prepares the slot in SAVE (`lea pc@(..),a0 ; moveq #0,d1`) | `0x14AC` | `0x1476` |
| "Save slot" entry (used by the tests) | `0x1450` | `0x141A` |
| "Restore checkpoint" entry | `0x4B16` | `0x4AD4` |
| Snapshot table (6 ranges, 664 bytes) | `0x4B9C` | `0x4B5A` |
| Initial stack (SSP, vector 0) | `0xFFE000` | `0xFFFFF0` |
| BUSACK loops | 8 | 12 |
| Ready-flag loops (`0xA00102`) | 5 | 5 (2 patched) |
| ROM checksum routine | present | removed |

**[OBSERVED]** The snapshot table holds the same `(offset, size)` pairs in both versions, so the variable offsets relative to `a5 = 0xFF026C` are the same and the position-independent routine `patches/sync_inventory.s` applies unchanged.

## 3. What was applied

### 3.1 ROM checksum (required)

**[OBSERVED]** Two calls, and only two (REA `xrefs` on `0x93FC` and `0x798`, plus a byte search for `4EB9 000093FC`):

- `0x486: jsr 0x93FC` at boot.
- `0x1630: lea pc@(0x794),a0 ; addqw #4,a0 ; jsr a0@`, inside the routine that writes SRAM (`0x1624`).

The routine at `0x93FC` (and its copy at `0x798`) does:

```
lea 0x474,a0 ; d0 = (a0)+            ; expected value, stored in the ROM itself
d7 = 15678 longs from 0x478          ; end-around-carry sum
d1 = ~sum - d0
a5@(20722) += d1                     ; a5+0x50F2 = the "MGSV" signature
```

**[INFERRED]** On an intact ROM `d1 = 0` and the signature stays `MGSV`. If any byte between `0x474` and `0xF96C` changes, the signature comes out different from `MGSV`. LOAD (`0x15F6: cmpl #'MGSV',d0`) then ignores the save.

**[OBSERVED]** The boot call (`0x486`) runs before the signature is written (`0x4EA`), so in practice only the SAVE call has an effect. The `RAM_CLEAR` (`0x4A0`) and `SAVE_SYNC` (`0x14AC`) patches fall inside the summed range.

**[OBSERVED]** In the simulator, the original v1.1 with one harmless changed byte (`0x4A3 ^= 1`) writes the signature `4D 47 53 55` (`MGSU`, difference `0xFFFFFFFF`) to SRAM. The fixed v1.1 writes `MGSV`.

**Decision:** both calls become NOPs (`0x486` 6 bytes, `0x1630` 8 bytes; `lea`+`addqw`+`jsr`). v1.2 removed the whole routine, so the behaviour is the same.

### 3.2 RAM clear

**[OBSERVED]** The routine at `0x49A` is called with `bsrs`, so its return address sits at the top of the stack, at `0xFFDFFC` (SSP `0xFFE000`). Clearing up to `0xFFFFEF` as v1.2 does would wipe that return address and the `rts` would jump to 0.

**Decision:** `movew #14331,d7` (`3E3C 37FB`) clears `0xFF0000-0xFFDFEF`. The game uses RAM up to `0xFF8456` (the highest absolute address it references), so everything it uses is covered.

**[OBSERVED]** In the simulator the original v1.1 reads uninitialised RAM at frame 11: `0xFF7C5E` (the sound state machine selector, `cmpiw #5,d0` at `0xFC02`) and `0xFF7D3A` (the saved interrupt level, read at `0x1144A`). The fixed ROM reads none. With 12 random-RAM seeds both original and fixed reach the game mode.

### 3.3 Z80 timeouts

**[OBSERVED]** Eight BUSACK waits (`movew $A11100,d0 ; btst #8,d0 ; bnes`): `0xF9F8`, `0xFA28`, `0xFA7C`, `0xFAFC` (absolute address), `0xFBA2` (`a2@`), `0xFD38`, `0xFDB6`, `0xFE1E` (`a0@`). A search for `08 00 00 08 66` confirms exactly these 8.

**[OBSERVED]** Five ready-flag waits, all with `a2 = 0xFD10` (reads the flag) and `a3 = 0x11814` (delay): `0xFF18`, `0x10548`, `0x10E80`, `0x10F0C`, `0x10FAC`. REA `xrefs` on `0xFD10` lists exactly these five loops.

**Decision:** same logic as v1.2 (`patches/z80_timeouts_v11.s`): `wait_busack` waits ~3.6 ms (`0x300` reads); `flagwait` waits up to 2,500 reads and preserves `d2`. `Z80_DEAD` lives at `0xFF9000`, outside the game's variables (maximum `0xFF8456`) and far from the stack. The five 20-byte loops become `jsr flagwait` + 7 NOPs, so they need no continuation address.

**[OBSERVED]** In the simulator with a Z80 that never answers, the original v1.1 does not reach the game mode and the fixed one does.

## 4. Checked and not applied

### 4.1 Wait loops on `0xA00160` (no timeout)

**[OBSERVED]** 19 reads of `0xA00160` (a Z80 status/command-queue byte, tested with `btst #0`, `btst #3` or `andib #3`). Eleven are entry reads (before entering the loop); eight are the loop itself.

Loop shape (SGDK compiler output, the same in all of them):

```
jsr  fa3c        release the Z80 bus
jsr  147c        re-enable interrupts
pea 5 ; jsr 11688   delay
jsr  144a        disable interrupts
pea 1 ; jsr f9e0    request the bus (waits for BUSACK)
moveb 0xA00160,d1   <- the loop read
addql #8,sp
btst #N,d1 ; bnes  <back to jsr fa3c>
```

| Loop read | Test | Note |
|-----------|------|------|
| `0x101AC` | bit 0 | function at `0x10158` |
| `0x10234` | bit 0 | function at `0x101DE` |
| `0x102FA` | bit 0 | function at `0x102A4` |
| `0x104D2` | bit 3 | function at `0x10444` |
| `0x10794` | bit 0 | function at `0x10742` |
| `0x108B4` | bit 0 | function at `0x10854` |
| `0x10972` | bit 0 | function at `0x10912` |
| `0x10A50` | `andib #3` | shared loop at `0x10A3E`, also reached from `0x10BE0` (entry reads at `0x10BD0`, `0x10C64`, `0x10C9C`) |

**[INFERRED]** If the Z80 keeps that byte "busy" forever (dead Z80, driver not loaded), the 68000 stays in these loops without a bound, the same black-screen symptom the BUSACK and flag timeouts address. v1.2 has equivalent loops (`0x1019A` and 6 others) and does not handle them either.

**[UNVERIFIED]** Proposed design, not implemented: replace the loop read (`moveb 0xA00160,d1`, 6 bytes) with a `jsr` to a routine that reads the byte and counts iterations in RAM (limit on the order of 1500). On overflow it returns the bit cleared and sets a second flag (`CMD_DEAD`, next to `Z80_DEAD`) so later calls leave after a single read instead of waiting the full limit on every command. It would need two variants (bit 0 and bit 3) and a third for the `andib #3` loop. The counter is zeroed when the bit is seen clear. Testing in the simulator would need a `Z80BUSY` mode that returns the busy byte. The time of one iteration was not measured, so the limit is a guess.

### 4.2 SGDK variables at ROM addresses

**[OBSERVED]** In v1.1 the code writes and reads ROM addresses in `0x13FE10-0x13FE5A`, inside the declared ROM end:

| Address | Use | Code |
|---------|-----|------|
| `0x13FE10` | tick counter (`addql #1`) | `0xF97C` |
| `0x13FE14` | `random()` seed (16-bit xorshift) | `0xF990` (set), `0xF9A8` (advance) |
| `0x13FE18`, `0x13FE1A`, `0x13FE1E`, `0x13FE22`, `0x13FE5A` | multitasking context (saved SR, counter, pointer, registers) | `0x12140`, `0x12158`, `0x1218A` |

The initial values read from the file are `0x00000001` at `0x13FE10`, `0xC427` at `0x13FE14` and zero at `0x13FE1A`.

**[OBSERVED]** Writes to ROM are ignored by the hardware (and by BlastEm).

**[OBSERVED]** REA `xrefs` for `0xF97C` and `0xF9A8` returns no references; the function at `0x12140` tests `tstl 0x13FE1A` (zero) and returns.

**[INFERRED]** This SGDK code (`random`, `setRandomSeed`, the tick counter, task switching) is linked but never called, so the write to ROM has no effect on the game. v1.2 has the same pattern (seed at `0x1BD854`).

**[UNVERIFIED]** If some code path called `random()` through an indirect jump the analysis did not resolve, the frozen seed (`0xC427`) would make it always return the same value. I found no such path.

### 4.3 Logic differences between v1.1 and v1.2

Normalized instruction diff (absolute addresses masked) over the game area, before the sound driver. **[OBSERVED]** The differences that are neither pointer shifts nor data tables:

| v1.1 | v1.2 | Note |
|------|------|------|
| `0xF68: cmpb #4,d0` (index in `a5@(7829)`, wraps to 0 at 4) | `cmpb #5` | **[INFERRED]** a 4-item list became 5 items; I did not identify which menu |
| `0x6A54: clrw a5@ ; rts` | `movew #1,a5@ ; rts` | the end of the routine now leaves the flag at 1 |
| (none) | `clrw a5@` at boot (`0x4C8`) and before a call (`0x6A18`) | the flag is cleared at more places |
| `0x27B0: tstb a5@(9160)` | removed | only affects flags, right before `moveb #1,a5@(9160)`: no effect |
| `0x486` and `0x1630`: ROM checksum | removed | see 3.1 |
| boot without `lea 0x1000000,sp` | `lea 0x1000000,sp ; bsrw 0x99C` | v1.2 moves the stack to the top of RAM |
| `jsr 0x9D2` (version/TMSS read) at `0x4F6` | removed | v1.2 handles the TMSS elsewhere |
| old SGDK sound driver | XGM2 | v1.2 uses the new driver (Z80 loops at `0x21Dxx-0x22Axx`) |

**[OBSERVED]** The word at `a5@(0)` is read by `tstw a5@` at `0x1F0`, `0x434` and `0x6880`. **[INFERRED]** It looks like a frame-sync flag. I did not establish whether the change at `0x6A54` fixes a defect, so **none of this was ported**.

## 5. How to reproduce

```
# REA: open_binary(path, format="raw-binary", architecture="m68k", entry_point="0x0")
#      search_bytes("08 00 00 08 66"), xrefs(0xfd10), xrefs(0x798)
m68k-linux-gnu-objdump -D -b binary -m m68k:68000 --start-address=0x486 --stop-address=0x4a8 "Metal Gear (v1.1).md"

python3 tests/run_tests.py --musashi /path/to/Musashi --game-version 1.1 --original "Metal Gear (v1.1).md"   # 11/11
MG_ROM_DIR=/folder/with/the/roms ./gradlew :app:desktopTest                                                   # includes the real ROM
```

## 6. Limits

- The fixed v1.1 was only run in the simulator and in BlastEm. **It was not tested on a real console or a flashcart.**
- None of the findings explains, on its own, the original hang seen on hardware; the Z80 timeouts remain the best hypothesis, not proof.
- The analysis of indirect calls is limited: REA/Ghidra does not resolve jumps through registers, so "never called" (4.2) holds for direct calls.
